<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| App state → URL (pushState) | Internal screen/tab/selection state is published into an attacker-visible address bar — must contain only whitelisted tokens |
| History traversal → app state | Back/forward replays untrusted URL strings (including entries typed or crafted by the user) back into React state |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-02-01 | Tampering | popstate/hashchange handler in apps/web/src/app.jsx | low | mitigate | State is derived only through parseRoute()'s whitelist; unrecognized fragments return without any state write, so crafted history entries cannot reach setScreen/setFocus |
| T-02-02 | Tampering | URL ↔ state desync (stale token, duplicate entries) | low | mitigate | pushState fires no hashchange (no echo), writes are skipped when the token already matches location.hash, and the handler's idempotence guard makes a double-fired traversal a no-op — refresh always agrees with the URL |
| T-02-03 | Information Disclosure | history entries reveal visited screens to anyone with the device | low | accept | Tokens expose only the screen name, dashboard tab and province-qualified municipality key already present in shared links; no user identity or secret is encoded (static PWA, handle-only identity elsewhere) |
| T-02-SC | Tampering | package installs | low | accept | No package-manager installs in this plan — the History API is a browser built-in; package-legitimacy gate not triggered |
</threat_model>
